# 0004 – Hosting the React SPA in Azure

**Status:** Proposed — awaiting user decision (deployment itself is M7)
**Date:** 2026-11-03

## Context

The brief suggests the SPA as an nginx container on Azure Container Apps (ACA), or Azure Static Web Apps (SWA) "if better". Constraints: cost-conscious/scale-to-zero, MSAL bearer tokens (no cookies) to the API, deep links (`/diary/2026/11`) must fall back to `index.html`, managed identity and azd-based deploy. The decision only affects M1 in one way: **the SPA must call the API on a relative `/api` path** so any same-origin option works, and a cross-origin option just needs a build-time base URL.

## Options

| | A. nginx container on ACA | B. Aspire `PublishAsStaticWebsite` (YARP container) on ACA | C. SWA Free + API on ACA (cross-origin) |
|---|---|---|---|
| Cost | ~€0 within ACA free grant (180k vCPU-s, 360k GiB-s, 2M req / subscription / month); image in ACR (ACR Basic ~€5/mo is needed for the API anyway) | same as A | SWA Free €0 (100 GB bandwidth, no SLA); API same as A |
| Cold start | page + API both scale from zero | same as A | page instant from CDN; API still cold-starts — the user waits for the first API call either way |
| Same-origin `/api` | yes, via nginx `proxy_pass` (hand-written config) | yes, `apiPath: "/api", apiTarget: api` generated by Aspire | no — CORS on API, `VITE_API_BASE_URL` baked at build. SWA "linked backends" / custom auth registrations are **Standard** only (~$9/mo) |
| Auth impact | none (MSAL in SPA, bearer to API) | none | CORS preflights on every call; SWA built-in auth unused |
| Complexity | own Dockerfile + nginx.conf (SPA fallback, headers, proxy) | minimal; generated by Aspire publish; SPA fallback behaviour **not yet verified** in docs | second hosting product, separate deploy target in `azure.yaml`, CORS config |
| Security headers / CSP | full control in nginx.conf | via YARP/ASP.NET config (less documented) | `staticwebapp.config.json` |

## Decision (proposed)

**B — Aspire `PublishAsStaticWebsite(apiPath: "/api", apiTarget: api)` on Container Apps**, falling back to **A (nginx)** if in M7 the generated YARP site cannot do SPA fallback or set the needed security headers.

Rationale: same-origin removes CORS and runtime-config problems; one hosting product and one deploy flow (azd + Aspire); cost is effectively zero within the ACA free grant; SWA's main advantage (no cold start for static files) is moot because the API cold-start dominates first load.

## Consequences

- M1: frontend always uses relative `/api/...`; Vite dev server proxies `/api` to `API_HTTPS || API_HTTP`. No CORS configured in the API.
- M7 must verify SPA fallback + headers on the YARP site and choose B or A; if the user picks SWA, add CORS + `VITE_API_BASE_URL` then.
