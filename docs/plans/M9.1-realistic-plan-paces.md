# M9.1 – Realistic plan paces: plan

**Status:** Approach approved by the user 2026-11-21 ("approved, go ahead"); this plan fixes the numbers and the contract. Branch `realistic-plan-paces`. A follow-up to [M9](M9-adaptive-training-plan.md), not a milestone. Decisions: [ADR 0039](../adr/0039-training-goals-and-realistic-target-estimate.md) and [ADR 0040](../adr/0040-training-plan-generation.md), both amended 2026-11-21 ("M9.1 realistic plan paces").

**Problem.** Generated plans train toward the user's target, not the runner's fitness. Example: last 10 runs at 6:00/km, goal half marathon under 1:40 (4:44/km) in 4 weeks. Today the reference pace is the target pace (4:44); the validator only rejects `paceMin < 0.85 × ref` and easy runs faster than `ref`, so tempo at ~4:30 and easy at 4:44 pass. The predictor uses only races and RPE ≥ 8 runs, so an easy-only diary gets no prediction and `targetMuchFasterThanPredicted` never fires.

## 1. Goal & acceptance criteria

1. **Train from current fitness.** The reference pace is the **slower** (larger s/km) of the target pace and the fitness pace (the prediction, else the existing `0.90 × mean pace` fallback). The goal pace appears in sessions only when fitness supports it.
2. **Fallback prediction from ordinary runs.** With no race and no RPE ≥ 8 run, `POST /api/goals/estimate` and plan generation get a `Low`-confidence prediction from recent training runs (basis kind `RecentTraining`). `targetMuchFasterThanPredicted` can then fire. `noRecentEffort` remains only for diaries with fewer than 3 usable training runs.
3. **Easy runs stay easy.** The faster bound of an easy or recovery session is never faster than `ceil(0.95 × recent easy pace)` (and never faster than the reference pace). Envelope, validator and repair enforce it.
4. **Say it in the plan.** When the target is more than 5 % faster than the fitness prediction, the plan aims at the predicted time, and the goal and plan UI show the "very ambitious" notice (wording in §3.6) with the existing **Use as target** action.
5. **Prompt and fact sheet.** Prompt `training-plan` **v4** (en + pl), fact sheet **v3** and envelope **v3** carry the fitness pace, the predicted time, the easy-pace bound and the flag.
6. **Eval.** The user's scenario (CI and live) passes: reference pace from fitness, no session faster than the bounds, flag set. The rest of the eval set still passes (live: ≥ 20/21 plans en, ≥ 20/21 pl; the previous run was 21/21).
7. **Nothing else regresses.** The demo plan and the rule-based fake plan stay repair-free and valid for every day of 2028. Existing goals and plans keep working unchanged until regenerated. Per-user isolation is unchanged (no new endpoint; every read stays `Owner`-filtered).

## 3. Contracts and numbers

### 3.1 Fallback prediction (ADR 0039 amendment)

Used only when `RaceTimePredictor` finds no race and no RPE ≥ 8 training run.
- **Runs:** completed **Training-category** runs dated `[today − 41, today]` (6 weeks), distance ≥ 3,000 m, duration > 0, effort pace `duration / (E / 1000)` within 150–900 s/km, where `E = distance + 10 × elevation gain` (the existing km-effort). **At least 3 runs**, else no prediction (`noRecentEffort`).
- **Basis:** `p` = the **median** effort pace and `E_b` = the median effort distance of those runs (an even count takes the mean of the two middle values). Median, so one fast or slow outlier does not move it.
- **Race-equivalent factor `0.90`** (`RaceTimePredictor.TrainingToRaceFactor`): `T_b = 0.90 × p × E_b / 1000`, i.e. a race over the runner's typical training distance is about 10 % faster than their typical training pace. Then the existing Riegel: `T_goal = T_b × (E_goal / E_b)^1.06`; pace and rounding as today.
- **Why 0.90 (the conservative end of the 0.88–0.90 rule of thumb):** the error we are fixing is overestimated fitness, so underestimating is the safer mistake (it only makes the plan gentler). The estimate is labelled `Low` confidence and "rough". A single race or hard run (RPE ≥ 8) replaces it at once. The median of mixed training already includes some steadier runs, so a larger speed-up would count them twice.
- **Result:** `confidence: Low` always; basis `kind: RecentTraining`, `runId: null`, `date` = the latest run used, `distanceMeters` / `elevationGainMeters` = the medians (elevation: median of the runs' gains, missing = 0), `durationSeconds` = `T_b` rounded, `runCount` = number of runs used.
- **Worked example (the user's scenario):** 10 runs × 8 km at 6:00/km, flat → `p` 360, `E_b` 8,000, `T_b` 2,592 s → half marathon **7,245 s (2:00:45), 343 s/km (5:43)**. Target 6,000 s < 0.95 × 7,245 → `targetMuchFasterThanPredicted`, value **17.2**.

### 3.2 Recent easy pace (ADR 0040 amendment)

`TrainingHistory.RecentEasyPaceSecondsPerKm` = the **median** pace (`duration / distance`, flat: these are real paces) of completed runs of type `easy`, `recovery` or `long` in the 4 complete ISO weeks before the current one (the window of `MeanPaceSecondsPerKm`), distance ≥ 1,000 m, pace 150–900. **At least 3 runs**, else `MeanPaceSecondsPerKm`, else null. Trail and treadmill runs are excluded (terrain or belt pace).

### 3.3 Envelope, validator, repair (ADR 0040 amendment)

| Item | Rule |
|---|---|
| `referencePaceSecondsPerKm` | `max(targetPace, fitnessPace)` when both exist; else whichever exists; `fitnessPace` = prediction pace (any basis), else `round(0.90 × mean pace)`; else null |
| `easyPaceMinSecondsPerKm` (new, envelope) | `max(ref, ceil(0.95 × recentEasyPace))`; either part alone when the other is null; null when both are null |
| `pace` (item-level drop, as today) | `paceMin < 0.85 × ref` (all sessions); **new:** intensity `racePace` with `paceMin < 0.97 × ref` (3 % band around the realistic race pace). The old "easy/recovery `paceMin ≥ ref`" part moves to `easyPace` |
| `easyPace` (new code, **repaired by clamp**) | intensity `easy`/`recovery` with `paceMin < easyPaceMin`: `paceMin := easyPaceMin`, `paceMax := clamp(old paceMax, paceMin, paceMin + MaxPaceSpreadSeconds)`; when the session has a duration whose implied pace is faster than the new `paceMin`, `duration := ceil(distanceKm × paceMin)`. If that pushes the session out of its own range (duration > 21,600 s, pace > 900), the session is **dropped** instead (counted in `droppedCount`). Plan-level safety net with `Value`/`Limit` for the retry note |
| Repair order | phase → pace-spread clamp → taperIntensity drop → `pace` drop → **`easyPace` clamp** → frequency drops → long-run clamp → weekly-volume scale |

**Why clamp, not drop, for easy runs:** with the slower reference pace many more easy sessions would trip the rule, and dropping them empties weeks (`emptyWeek` → retry → `plan-failed`). Making an easy run slower is the "easier or safer" kind of repair the step allows. Hard sessions keep the drop: a too-fast interval session cannot be fixed by moving one number.

Not in M9.1 (open question 2): checking the implied pace of sessions without a pace range.

### 3.4 Estimate API (additive except one nullability)

```ts
GoalEstimateResponse.prediction.basis = {
  runId: string | null;            // CHANGED: null for kind "RecentTraining"
  date: string; kind: "Race" | "Training" | "RecentTraining";   // NEW value
  distanceMeters: number; durationSeconds: number; elevationGainMeters: number | null;
  runCount: number }               // NEW: 1 for Race/Training
```
The SPA is the only client and does not read `runId`; the generated schema is regenerated in the same PR.

### 3.5 Plan metadata (one nullable column; flag computed at read time)

- **Migration `PlanPredictedDuration`** (additive, ADR 0032 expand rule): `Goals.PlanPredictedDurationSeconds int NULL`, written by `Goal.RecordPlan` on every model plan and the demo plan (= the prediction's duration at generation time, any basis; NULL when there was none). Plans before M9.1 stay NULL.
- **API** (computed in the mapping, no history read):

```ts
GoalDto.plan += {
  ambitiousTarget: boolean;          // targetDurationSeconds != null && PlanPredictedDurationSeconds != null
                                     //   && targetDurationSeconds < 0.95 × PlanPredictedDurationSeconds
  trainsTowardSeconds: number | null // PlanPredictedDurationSeconds when ambitiousTarget, else null
}
```
- **Why stored, not recomputed on read:** the notice must describe what *this* plan was built for. Recomputing would read 112 days of runs per goal on every `GET /api/goals` and would drift as new runs are logged. Storing the whole flag is not needed: a change of the target sets `PlanOutdated`, so comparing the stored prediction with the current target is exact for any plan that is not outdated. The UI hides the notice when `plan.outdated` is true (the "Goal changed since this plan" banner already takes its place).

## 4. Risks and open questions

**Risks**
- **Existing goals and plans are unaffected until regenerated** (no stored suggestion changes; `PlanPredictedDurationSeconds` NULL → no notice). The realistic-target hint changes at once for everyone (computed). Suggestions are not cached anywhere else.
- **Slower plans for runners whose easy pace understates their fitness.** Accepted (§3.1): the estimate is labelled, a race or RPE ≥ 8 run overrides it, and the user can keep their target.
- **Long horizons:** the plan trains from today's fitness for up to 16 weeks and does not assume improvement. Regenerating every few weeks picks up progress (open question 3).
- **Model reliability:** new rules mean more repairs. The clamp keeps plans whole; the live eval measures it (G-RP1).
- **Demo plan:** the demo goal is a `Distance` goal without a target and its sessions have no pace ranges, so the new rules cannot touch it; the "repair-free for every day of 2028" test must still pass (and the fake plan writer must use `easyPaceMinSecondsPerKm`).
- **Guests:** same rules, same quotas; the demo plan gets `PlanPredictedDurationSeconds` from its own estimate and `ambitiousTarget` is false (no target).

**Open questions (defaults in bold; implementation proceeds with them unless the user objects)**
1. Race-equivalent factor: **0.90** (alternative 0.88: a ~2 % faster estimate).
2. Check the implied pace (distance/duration) of easy sessions without a pace range? **Not in M9.1** (durations are estimates; revisit if the live eval shows fast implied paces).
3. Suggest regenerating in the notice for long horizons ("regenerate in a few weeks as you get fitter")? **No** (keep the agreed wording).
